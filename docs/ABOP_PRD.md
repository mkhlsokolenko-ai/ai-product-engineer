# ABOP v1.0 — Product Requirements Document

**Продукт:** ABOP (Agent-Based Operations Platform) — рантайм исполнения агентов
**Версия документа:** 1.0
**Статус:** draft, к утверждению
**Связанные документы:** `ABOP_ARD.md` (архитектура), `ABOP_ADR.md` (решения), `ABOP_TDR.md` (технические детали)
**Внешние зависимости:** LUDA v2 (PRD, ADR, TDR, AOP) — 3 контракта; sLAVA (RAG-контур)
**Полигон принципов:** CLI `ape` (`cli/ape.py`) — обкатка онтологии/волн/Blackboard/Data Plane перед переносом в ABOP

---

## 1. Одним абзацем

ABOP — рантайм, который исполняет агентов **в верифицированном конверте безопасности** внутри регулируемого периметра (ФСТЭК / ФЗ-152 / ДСП). На входе — задача и три контракта от LUDA (`CapabilityRequest`, `DeploymentContract`, `BaselineMeasurement`), задающие, что должно уметься, на каких условиях и как измерять эффект. Внутри — онтология ролей (Семья → Роль → Навык), безопасность на уровне отдельного навыка, оркестрация волнами (не свободный цикл), агент-нативный слой данных (Data Plane) и governance-петля, которая выводит Definition of Done и сверяет с ним результат. На выходе — исполненная работа с провенансом, журналом стоимости и аудитом каждого перешага. ABOP не решает сам, сколько автономии дать агенту, — это решает LUDA; ABOP не может превысить `autonomy_level` из `DeploymentContract`.

Продуктизация LUDA v2 как рантайма, эволюция VRATA на паттернах openclaw. Отдельный продукт и репозиторий; связь с LUDA/sLAVA — только версионированные контракты.

## 2. Что ABOP делает и почему именно так

VRATA был спроектирован как оркестратор потоков «агент = процесс»: один процесс — один агент, свободный ReAct-цикл, tool-calling без разделения данных и инструментов, безопасность на уровне контура, а не действия. Четыре причины пересобрать его в ABOP.

### 2.1. Агент потребляет данные не как человек

Главный тезис архитектуры (`ABOP_ARD` §1): системы отдают данные «для глаз» — HTML, UI, PDF, разрозненные API. Агенту нужен типизированный, самоописываемый, стабильный JSON с известной схемой, провенансом и свежестью. Скрейпить человеческие интерфейсы каждым агентом — хрупко, дорого, недетерминированно, и делает поведение агента невоспроизводимым, а значит неаудируемым.

**Решение:** между системами и агентами вводится **Data Plane** — слой адаптеров источник → каноническая сущность → контракт данных, выдающий агенту предсказуемый JSON через `data_query` (см. ABOP_ARD §3, ADR по Data Plane).

### 2.2. Свободный цикл неаудируем в регулируемом периметре

Автономный ReAct-агент, который сам решает следующий шаг из произвольного набора инструментов, не даёт заранее известной границы поведения. Для ДСП/ФЗ-152 это неприемлемо: нельзя предъявить службе ИБ гарантию, что агент не выйдет за scope.

**Решение:** оркестрация **волнами** (fan-out / fan-in), а не свободный цикл. Состав волны, набор навыков и переходы между ролями фиксируются и журналируются; поведение агента детерминировано в границах контракта (см. ABOP_ARD §5).

### 2.3. Безопасность контура — слишком грубая гранула

Разрешение «этот агент может писать наружу» на уровне всего агента означает, что один опасный навык открывает весь периметр. Read-only анализ и необратимое действие требуют разного режима.

**Решение:** безопасность объявляется **на уровне навыка** — тройка `mode` (read/write/action) × `egress` (internal/external) × `cite`. `action` → `dry_run` + HITL; `external` → анти-инъекция + PII-маска; `cite` → числа только из источника (см. ADR по модели безопасности навыка).

### 2.4. Автономия должна назначаться диагнозом, а не рантаймом

Если рантайм сам решает, сколько работы отдать агенту, продавать диагностику отдельно бессмысленно, а гарантию автономии нечем подтвердить перед аудитом заказчика.

**Решение:** ABOP **принимает** уровень автономии из `DeploymentContract` LUDA и не может его превысить. Это единственная обязательная связь между продуктами (см. ADR по стыку с LUDA).

### 2.5. Что сознательно оставлено жёстким

- Оркестрация — только волнами. Возврат к свободному ReAct-циклу рассмотрен и отклонён: он ломает аудируемость.
- Числа — только из источника (`cite`). Ни один навык не «додумывает» значения; отсутствие данных — это результат, а не повод к генерации.
- Автономия сверху ограничена контрактом LUDA всегда, включая «мы только на тестовом контуре».
- Рецепты данных — декларативны и пишутся человеком; исполняемый код в рецепт данных не попадает (см. §6, ABOP_ARD §3.6-bis).

## 3. Проблема

### 3.1. Со стороны заказчика

Компания хочет отдать часть операционной работы агентам, но упирается не в модель, а в две стены.

1. **Данные не готовы для агентов машиночитаемо.** Агенту приходится парсить те же интерфейсы, что и человеку. Каждый новый агент переизобретает извлечение из почты, трекера, ERP; результат хрупок и ломается на любом изменении верстки или формата. Нет стабильного слоя, из которого агент берёт типизированные сущности с известной схемой и происхождением.

2. **Нет безопасного аудируемого рантайма ролей в регулируемом периметре.** Существующие оркестраторы дают либо свободный автономный цикл (неаудируемо, служба ИБ не согласует), либо жёсткий пайплайн без ролей и памяти (не покрывает реальную работу аналитика/финансиста). Между ними нет продукта, который исполняет роли с навыками, держит автономию в границах контракта и оставляет аудит-след на каждый перешаг.

### 3.2. Со стороны поставщика (нас)

LUDA ставит диагноз готовности и выпускает контракты, но контракт без рантайма, который его исполняет и **соблюдает**, — это отчёт в стол. Нужен исполнитель, который принимает `DeploymentContract` как закон, а не как рекомендацию, и предъявляет доказательство соблюдения.

### 3.3. Почему это отдельный продукт

Диагностика (LUDA) и исполнение (ABOP) покупаются в разные моменты и разными бюджетами: диагноз — до решения о пилоте, рантайм — после. У них разные релизные циклы и разные критерии приёмки. Общий репозиторий связал бы их в узел, блокирующий оба. Связь — только через версионированные схемы контрактов.

## 4. Границы продукта

### В границах

- **Рантайм агентов:** онтология Семья → Роль → Навык, переключение (`use_skill` / `become` / `handoff`), оркестрация волнами, Blackboard.
- **Data Plane:** адаптеры источник → каноническая сущность → контракт данных; выдача агенту через `data_query` / `data_get` / `data_schema`.
- **Безопасность и HITL:** режим навыка (read/write/action × internal/external × cite), `dry_run` + подтверждение оператора для действий, анти-инъекция и PII-маска для egress.
- **Память:** Blackboard (рабочая, event-sourced), долговременная с забыванием по TTL от критичности, диалоговая (дистилляция).
- **Governance-петля:** агент-аудитор выводит Definition of Done, сверяет результат, инициирует ремедиацию.
- **Инфраструктура вызова:** FastMCP-шлюз + Keycloak JWT, единый контракт `session_id` + JWT + `cost_journal`.

### Вне границ

- **Аудит готовности процесса** к передаче агенту, вывод уровня автономии, выпуск контрактов. Это LUDA.
- **RAG по нормативке**, разбор неструктурированных корпоративных знаний, ответы с цитатами из корпуса документов. Это sLAVA.
- **Обучение и хостинг моделей.** ABOP использует готовые LLM (внутренние/через прокси sLAVA), не обучает их.
- **Портфельная приоритизация** инициатив. Это MIRA.
- **Решение о допустимой автономии.** ABOP исполняет в рамках контракта LUDA, но не назначает автономию сам.

### Продуктовая лестница

```
MIRA        →  LUDA         →  sLAVA          →  ABOP
портфель       диагноз          восполнение       исполнение
инициатив      готовности       контекста         процесса
               процесса         (RAG/норматив)    (агенты, рантайм)
```

MIRA приоритизирует, LUDA ставит диагноз готовности и выпускает контракты, sLAVA восполняет контекст и нормативную базу, ABOP исполняет процесс агентами в границах контракта. ABOP — последнее звено: без диагноза (LUDA) исполнять нечего и незачем.

## 5. Пользователи

| Роль | Кто это | Что делает в ABOP | Что получает |
|---|---|---|---|
| **Заказчик** | Владелец процесса, ИТ/финансовый директор | Согласует запуск агента в рамках контракта LUDA, читает результат и аудит | Исполненная работа + доказательство соблюдения конверта безопасности |
| **Доменный эксперт** | Методолог, аналитик, отраслевик | Пишет декларативные рецепты данных (источник → canonical) и специализированные навыки семьи | Переиспользуемое между задачами формализованное знание |
| **Оператор** | Дежурный, контролёр процесса | Обрабатывает HITL-подтверждения для действий (`action` / `dry_run`), разбирает исключения | Точки контроля ровно там, где действие необратимо или уходит наружу |
| **Платформа (LUDA)** | Продукт-источник контрактов | Поставляет `CapabilityRequest` / `DeploymentContract` / `BaselineMeasurement` | Гарантию, что рантайм не превысит выданную автономию |

Явно: ABOP не рассчитан на бесконтрольное самообслуживание. Автономия агента определяется контрактом, действия проходят через HITL там, где так предписано. Это влияет на весь UX рантайма и на модель ответственности.

## 6. Ключевые концепции

**Семья ролей (Role Family)** — верхний уровень онтологии: класс работ с общим контекстом. Реализовано 10 семей: 4 бизнес (Аналитика, Финансы, Архитектура, Менеджмент) + 6 инженерных. Семья Аналитики содержит 5 ролей: финансовый, системный, дата-, бизнес- и процессный аналитик.

**Роль (член семьи)** — конкретный исполнитель внутри семьи со своим набором навыков. Агент становится ролью через `become`.

**Навык (Skill)** — атомарная способность с телом. Реализовано 37 навыков. Два яруса: **глобальные** (доступны из CLI) и **специализированные** (живут внутри семей). Раскрываются прогрессивно (`use_skill`, progressive disclosure) — агент не видит весь арсенал сразу.

**Безопасность навыка** — тройка, объявленная на самом навыке: `mode` (read / write / action) × `egress` (internal / external) × `cite`. Гарантии: `action` → `dry_run` + HITL; `external` → анти-инъекция + PII-маска; `cite` → числа только из источника. Это и есть «конверт безопасности» на уровне гранулы действия.

**Переключение** — три механизма смены исполнителя/контекста: `use_skill` (раскрыть навык), `become` (сменить роль), `handoff` (передать эстафету через доску другому агенту).

**Волна (fan-out / fan-in)** — единица оркестрации: агенты запускаются параллельно (fan-out), их результаты собираются на барьере (fan-in), следующая волна видит доску. Не свободный цикл — граница поведения известна заранее.

**Три плоскости** — Agent Plane (агенты / волны / Blackboard) + Tool Plane (примитивы + рецепты) + Data Plane (агент-нативный слой данных). Рецепт = кто думает (Agent) + чем делает (Tool) + на каких данных (Data). Подробно — ABOP_ARD §2–4.

**Data Plane** — слой, превращающий разнородные источники в канонические машиночитаемые сущности: Source Adapter → Canonical Schema → Data Contract → `data_query`. Агент берёт данные только так, не парся человеческие форматы.

**Data Recipe (рецепт данных)** — декларативное (YAML/JSON) описание перевода источника в каноническую сущность, которое пишет **человек** (доменный эксперт), без исполняемого кода, валидируется схемой, версионируется. Не путать с Agent Recipe (плейбук агента). См. ABOP_ARD §3.6-bis.

**Blackboard** — рабочая память прогона: event-sourced, append-only, состояние = свёртка событий, воркеры stateless. Разделяет «что агенты уже надумали в этой задаче» (Blackboard) и «что есть в системах машиночитаемо» (Data Plane).

**Долговременная память с забыванием** — записи живут по TTL от критичности: operational 7 дней, important 90 дней, critical 365 дней, regulatory 5 лет, permanent ∞. Диалоговая память — с дистилляцией в конспект.

**Governance-петля** — агент-аудитор выводит Definition of Done для задачи, сверяет с ним результат исполнения и, при расхождении, инициирует ремедиацию. Замыкает исполнение на проверяемый критерий готовности.

**Три контракта LUDA** — вход от диагноза: `CapabilityRequest` (что должно уметься), `DeploymentContract` (на каких условиях, включая `autonomy_level` и точки HITL), `BaselineMeasurement` (как процесс работает сейчас, для замера эффекта).

**Единый контракт вызова** — любой вызов (tool или data) идёт через MCP-шлюз: `session_id` + JWT + запись в `cost_journal` → структурный результат с провенансом.

## 7. Что ABOP не делает, хотя его об этом попросят

- **Не повышает автономию сверх контракта LUDA.** Просьба «дай агенту просто всё сделать самому» упирается в `autonomy_level` из `DeploymentContract`. Хотите выше — переаудит в LUDA.
- **Не отвечает по нормативке из своего корпуса.** Вопрос «а что говорит ГОСТ» уходит в sLAVA; ABOP исполняет, а не ищет по документам.
- **Не диагностирует готовность процесса.** «Скажите, можно ли это вообще отдать агенту» — это LUDA, до ABOP.
- **Не додумывает числа.** Навык с `cite` берёт значения только из источника; отсутствие данных фиксируется как результат.
- **Не даёт человеку писать исполняемый код в рецепт данных.** Рецепт данных декларативен и валидируется схемой — иначе рухнул бы канон Data Plane.

Фиксируется, чтобы не размывать границы продукта и лестницу.

## 8. Метрики успеха продукта

| Метрика | Смысл |
|---|---|
| Доля прогонов, не превысивших `autonomy_level` контракта | 100% — жёсткий инвариант, а не цель |
| Доля действий (`action` / `external`), прошедших HITL / `dry_run` до исполнения | 100% |
| Доля результатов, прошедших governance-петлю (сверка с Definition of Done) | цель — все задачи с объявленным DoD |
| Доля данных, взятых агентом через Data Plane (`data_query`), а не скрейпингом | рост к 100% по мере покрытия источников адаптерами |
| Полнота аудит-следа: каждый перешаг в `cost_journal` с провенансом | 100% |
| Число семей/навыков, добавленных без правки ядра рантайма | расширяемость онтологии |

Первые две метрики — проверка того, что «верифицированный конверт безопасности» реален, а не декларативен.

## 9. Открытые вопросы

1. **Хранилище Data Plane и долговременной памяти в проде** — конкретный движок и место RAG-слоя над каноническими сущностями (см. ABOP_ARD §8, ABOP_TDR).
2. **Первая вертикаль/источник** для сквозного прогона (почта / трекер / CSV — обкатка в `ape`; в проде — стык с вертикалью LUDA).
3. **Мультитенантность источников** — общие креды vs BYO на арендатора.
4. **Физическое переиспользование** шлюза / Keycloak / LLM из полигона `ape` в регулируемом периметре ABOP (egress через прокси sLAVA, PII-маскирование).
5. **Формат редактора Data Recipe** (no-code UI + предпросмотр на реальной выборке) на фронте ABOP.
6. **Ценообразование** ABOP относительно LUDA: отдельная лицензия рантайма или связка с диагнозом.
