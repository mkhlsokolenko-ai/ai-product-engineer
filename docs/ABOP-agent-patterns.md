## Часть I. Анатомия агента (к Лекции 6)

Агент в ABOP — это НЕ «один большой промпт». Это **граф узлов** под контрактом, где каждый узел
имеет тип и роль:

```
[Триггер] → [Источник данных] → [Навык] → [Навык] → [HITL] → [Выход]
 старт        Data Plane        skill      skill    человек    доставка
```

Типы узлов: `trigger` (стартовое событие), `source` (данные), `skill` (умение),
`llm` (ветвление), `hitl` (подтверждение человеком), `out` (выходное действие).

**Большая картина: как агент живёт в окружении**

```
                          ┌──────────── КОНВЕРТ GOVERNANCE (контракт) ────────────┐
                          │  автономия ≤ потолок · HITL на действиях · аудит       │
                          └───────────────────────────────────────────────────────┘
                                              ▲ проверка (assembly.check_graph)
                                              │
   Контракт LUDA ──ingress.validate()──► [АГЕНТ = граф узлов]
                                              │
        ┌─────────────────────────────────────┼───────────────────────────────────┐
        ▼                                       ▼                                    ▼
   ┌─────────┐        ┌──────────────┐   ┌──────────────┐                    ┌──────────┐
   │ ТРИГГЕР │───────►│  ИСТОЧНИКИ    │──►│   НАВЫКИ      │──► HITL ─────────►│  ВЫХОД   │
   │ старт   │        │ (Data Plane) │   │ (skills)     │    подтверждение   │ (OUT)    │
   └─────────┘        └──────┬───────┘   └──────┬───────┘                    └────┬─────┘
   расписание/               │ data_query        │ LLM объясняет                  │ dry_run
   событие                   │ (только своё,     │ находки кода                   │ по умолч.
                             │  ABAC-гейт)       │                                │
                             ▼                   ▼                                ▼
                    ┌────────────────┐   ┌──────────────┐              почта · трекер · вики
                    │ Внешние системы│   │ КОД: детекция│              (реальная отправка —
                    │ 1С/CRM/трекеры │   │ (истина)     │               только под HITL)
                    └────────────────┘   └──────┬───────┘
                             ▲                   │ + RAG-нормы (провенанс)
                             │                   ▼
                   адаптеры/рецепты      ┌──────────────┐
                   (register_adapter)    │ Корпус знаний│  (изолирован по семье, ABAC)
                                         └──────────────┘

   ═══ Сквозь всё: trace_id · метрики · кэш результатов · координация реплик ═══
```

### Паттерн 1. Детекцию считает КОД, объясняет — LLM (grounded generation)

**Проблема.** Если просить LLM «найди нарушения в данных» — он галлюцинирует числа и пропускает
случаи. Нельзя доверять аудит/финансы генеративной модели.

**Решение.** Разделяем два слоя:
- **Факты/находки** считает **детерминированный код** на ПОЛНЫХ данных (воспроизводимо, с доказательством).
- **LLM только ОБЪЯСНЯЕТ** уже найденное (суть, риск, что проверить) — он не источник истины, а «редактор».

**Где в коде.**
- Детектор: `cli/ape.py` → `audit1c_run_checks()` (строит находки классов A/B/C/D по графу
  документов, каждая со ссылкой на запись и доказательством), `audit1c_build_graph()`,
  `audit1c_trace_chains()` (трассировка цепочек операций).
- Grounding: `server/web_api.py` → `execute_agent_run()` считает находки ДО LLM и прокидывает их в
  `server/runner.py` → `run_live(..., findings_context=...)`. Внутри `run_live` навык получает готовые
  находки и **объясняет** их, а не ищет заново (`_findings_context_text()` формирует контекст).

```
   ПОЛНЫЕ данные            ┌───────────────────────┐   находки (истина,
   (canonical store) ──────►│ КОД-детектор          │──► с доказательством) ──┐
                            │ audit1c_run_checks()  │   [A] нет себестоимости  │
                            └───────────────────────┘   [B] нет счёта-фактуры  │
                                                                               ▼
   методика навыка ────┐                                   ┌───────────────────────────┐
   дайджест данных ────┼──────────────────────────────────►│ LLM (навык)               │
   найденные находки ──┘  findings_context                  │ ОБЪЯСНЯЕТ: суть/риск/     │
                                                            │ что проверить + норма     │
                                                            └───────────────────────────┘
                                                                   │
   ✗ LLM НЕ ищет заново (иначе на сэмпле скажет «ничего нет»)      ▼
   ✓ LLM объясняет РЕАЛЬНЫЕ находки кода                    нарратив для человека
```

**Чему учит.** *Ответственность за корректность — на коде; LLM отвечает за форму, не за факты.*
Это ключевой принцип надёжного агента в регулируемой области.

### Паттерн 2. Governance-конверт: автономия ≤ потолок, действия наружу — под HITL

**Проблема.** Агент не должен сам делать необратимое (отправить письмо, изменить систему) выше
разрешённого уровня.

**Решение.** У каждого агента есть **конверт** из контракта: максимальный уровень автономии (A0–A4)
и точки HITL. Перед запуском граф проверяется: автономия узла ≤ потолок; узел с внешним действием
(`mode=action`, `egress=external`) обязан быть под HITL.

**Где в коде.** `server/assembly.py` → `check_graph()` (валидация перед сохранением агента);
`server/runner.py` → `run_agent()` формирует HITL-гейты и governance-вердикт (DoD-проверки).

**Чему учит.** *Безопасность агента — это не «доверие модели», а проверяемые инварианты вокруг неё.*

### Паттерн 3. Контракт на входе (Contract Ingress)

**Проблема.** Откуда агент «знает», что ему можно, какие навыки, какой потолок?

**Решение.** Агент рождается из **версионированного контракта** (что за процесс, семья, навыки,
потолок автономии, метрики приёмки). Контракт валидируется на приёме — не доверяем вслепую.

**Где в коде.** `server/ingress.py` → `validate()` (проверка схем, evidence, автономии);
`server/web_api.py` → `demo_prepare()` (идемпотентно: контракт → сохранённый агент → запуск).

**Чему учит.** *Граница между продуктами — версионированный контракт, а не общий код.*

## Часть II. Взаимодействие с системами и окружением (к Лекции 4)

Агент бесполезен без данных и без действий во внешний мир. Здесь — как ABOP это организует
безопасно и единообразно.

### Паттерн 4. Data Plane: источники → канонические сущности по ключу `entity`

**Проблема.** Данные разбросаны по системам (1С, CRM, трекеры) в разных форматах. Агент не должен
знать про форматы и лазить в системы напрямую.

**Решение.** **Рецепт** (recipe) описывает: источник → преобразование → каноническая сущность
(`doc1c`, `transaction`…). Агент читает ТОЛЬКО каноничные данные через единый интерфейс `data_query`,
не зная, откуда они. Ключ связи во всей системе — `entity`.

**Где в коде.** `cli/ape.py` → `register_adapter()` (реестр адаптеров источников: csv/http/postgres/
vector/…), `data_query()` (единое чтение канонического стора).

```
  ВНЕШНИЕ СИСТЕМЫ          РЕЦЕПТ (recipe)              КАНОНИЧЕСКИЙ СТОР        АГЕНТ
  ┌──────────┐          ┌────────────────┐          ┌──────────────────┐   ┌─────────┐
  │ 1С       │─адаптер─►│ источник →      │─emit────►│ entity: doc1c    │◄──│ навык   │
  │ CRM      │  http    │ преобразование →│ (версия) │ entity: transaction│  data_query
  │ трекер   │  sqlite  │ entity          │          │ entity: customer │   │ (не знает
  └──────────┘  postgres└────────────────┘          └──────────────────┘   │  про 1С)│
   сырьё,                 «как достать и                провенанс+версия     └─────────┘
   разные форматы          привести к сущности»          на каждой записи

  Ключ связи ВСЮДУ = entity.  Меняешь рецепт → меняется entity → видят все, кто на неё завязан.
```

**Чему учит.** *Разделяй «добычу данных» и «использование данных». Агент работает с контрактом
данных, а не с сырыми системами.*

### Паттерн 5. Версионное хранилище: последняя версия не «протухает» по времени

**Проблема.** Наивный TTL («данные старше суток — невалидны») удаляет актуальный снимок, если его
давно не обновляли. Демо/отчётность на закрытом периоде ломается.

**Решение.** **Версионная свежесть**: `data_query` всегда отдаёт ПОСЛЕДНЮЮ созданную версию записи
(по `provenance.fetched_at`); по TTL вытесняются только ПЕРЕКРЫТЫЕ более новыми версиями старые записи.
Данные не исчезают, пока их не заменили свежими.

**Где в коде.** `cli/ape.py` → `_fresh()` (freshness перекрытых версий), `data_query()` (dedup по id →
последняя версия), `_data_compact()` (физически вытесняет старьё при записи новой версии).

```
  Наивный TTL (ПЛОХО):                    Версионная свежесть (ХОРОШО):
  запись v1 (5 дней назад)                id=X  v1 (5 дней) ─┐
     └─ TTL 24ч истёк → УДАЛЕНА              id=X  v2 (сегодня)─┴─► data_query отдаёт v2
        data_query → пусто → 0 находок       (последняя версия НЕ протухает по времени)
                                             id=Y  v1 (5 дней), новее нет → отдаётся v1
        ✗ актуальный снимок пропал             ✓ старьё уходит ТОЛЬКО когда перекрыто новым
```

**Чему учит.** *Свежесть данных — это про версии, а не про часы на стене. Durability > «удобный TTL».*

### Паттерн 6. Least-privilege / ABAC: агент видит только своё

**Проблема.** Агент-аналитик не должен читать данные архитектуры; финансовый — гитею и т.п.
Изоляция по доступу критична в мультикомандной среде.

**Решение.** Доступ к системе/знанию проверяется **по семье агента** (атрибутный контроль, ABAC).
Знание (RAG) изолировано по тенанту на семью. Закрытые сущности не попадают в прогон — честно
помечаются, а не «молча пропадают».

**Где в коде.** `server/access.py` → `can_reach_system()`, `manifest()` (least-privilege манифест),
`qdrant_tenant()` (тенант знаний на семью); `server/web_api.py` → `_gate_agent_data()` (ABAC-гейт на
данных прогона: `blocked_entities`).

```
   Агент семьи «аналитика»           ШЛЮЗ (ABAC)              Ресурсы
        │                      ┌──────────────────┐    ┌──────────────────┐
        │  запрос доступа ────►│ can_reach_system │───►│ ✓ данные аналитики│
        │                      │ (по семье агента)│    │ ✓ корпус знаний   │
        │                      │                  │    │   своей семьи     │
        │                      │                  │──✗─│ ✗ данные архитект.│ ← отказ+аудит
        │                      └──────────────────┘    │ ✗ чужой тенант    │
        ▼                        qdrant_tenant(семья)  └──────────────────┘
   закрытые сущности                                    Знание изолировано
   НЕ попадают в прогон                                 по тенанту на семью
   (честно помечены, не «молча пропали»)
```

**Чему учит.** *Права — атрибут агента (кто он), а не жёстко зашитый список. Проверка на шлюзе, не в
каждом навыке.*

### Паттерн 7. Стартовое событие (триггер) с политикой инстанциации

**Проблема.** Кто и когда запускает агента? Как контролировать «размножение» экземпляров?

**Решение.** Узел `trigger` в графе несёт тип старта (расписание/событие/ручной) и **spawn-политику**:
кого создавать, сколько (1 или per-item), под HITL ли создание, потолок автономии. Планировщик
исполняет политику, а не просто «дёргает».

**Где в коде.** `server/triggers.py` → `triggers_of()` (извлечь триггеры из графа), `fire()`
(spawn-политика + governance), `scheduler_loop()` (фоновый тик).

```
   ИСТОЧНИК СТАРТА                 ТРИГГЕР (узел графа)          SPAWN-ПОЛИТИКА
   ┌──────────────┐              ┌──────────────────┐       ┌──────────────────┐
   │ расписание   │              │ тип старта       │       │ кого создавать   │
   │ (cron)       │─────────────►│ + условия        │──────►│ сколько (1|N)    │──► ЗАПУСК
   │ событие      │              │                  │       │ HITL на создание?│    экземпляра(ов)
   │ (в системе)  │              │                  │       │ потолок автономии│
   │ вручную      │              └──────────────────┘       └──────────────────┘
   └──────────────┘               scheduler_loop → fire()    (не просто «дёрнуть»,
                                                              а регламент создания)
```

**Чему учит.** *Регламентируется не только «что делает агент», но и «как он создаётся».*

### Паттерн 8. Выходное событие (OUT): доставка с dry_run и HITL по умолчанию

**Проблема.** Результат надо доставить (письмо, задача в трекере, документ) — но случайная реальная
отправка недопустима.

**Решение.** Узел `out` конфигурирует канал/адрес/формат. По умолчанию — **dry_run** (превью);
реальная отправка только при явном флаге И вне HITL. Единый механизм доставки поверх разных каналов.

**Где в коде.** `server/web_api.py` → `_deliver_out_nodes()` (проброс OUT в доставку),
`_build_report_html()` (отчёт из находок); `cli/ape.py` → инструменты доставки (`_t_*` для почты/
вики/PDF/таск-трекера) — все с политикой «dry_run пока не подтверждено».

```
   находки+нормы ──► отчёт ──► узел OUT ──► КАНАЛ (почта/трекер/вики/PDF)
                              (канал,          │
                               адрес,          ├─ dry_run (по умолчанию) ─► только превью, наружу НЕ ушло
                               формат)          │
                                                └─ реальная отправка ─► ТОЛЬКО если: флаг «real» ВКЛ
                                                                        И вне HITL И есть доступ
   Безопасно по умолчанию: случайно ничего не улетит.
```

**Чему учит.** *Побочные эффекты во внешний мир — под явным подтверждением. Безопасно по умолчанию.*

### Паттерн 9. RAG-заземление норм (знание из корпуса, а не из памяти модели)

**Проблема.** LLM «помнит» законы неточно и выдумывает номера статей.

**Решение.** Норму под находку подтягиваем из **корпуса знаний семьи** (RAG) по тексту находки и
цитируем; поле «норма» — только реальная статья, иначе пусто.

**Где в коде.** `server/web_api.py` → `_agent_knowledge_fn()` (RAG-функция с ABAC-гейтом),
`server/runner.py` → `run_live` инжектит знание навыкам с флагом `cite`.

**Чему учит.** *Факты о мире — из источника с провенансом, не из весов модели.*

## Часть III. Оптимизация работы агента

Здесь — как мы сделали прогон быстрым и дешёвым, НЕ трогая качество. Все замеры — на одном сценарии
(аудит 1С, 10 находок). Итог: **~357 с → ~40 с (≈9×)**, стоимость LLM почти в ноль, находки 1:1.

**Путь оптимизации (каждый шаг — замер, качество 1:1):**

```
  исходно            + дайджест        + свой LLM,       + structured      + grounded
  (полный дамп,      данных            параллелизм       output (JSON)     объяснение
   внешний LLM)      (Паттерн 10)      (Паттерн 12)      (Паттерн 11)      (Паттерн 1)
  ┌────────┐         ┌────────┐        ┌────────┐        ┌────────┐        ┌────────┐
  │ 357 с  │───────► │ 110 с  │──────► │  77 с  │──────► │  28 с  │──────► │ ~40 с  │
  │ находки│         │ токены │        │ парал- │        │ нет    │        │ нарратив
  │  вода  │         │  ↓ 8×  │        │ лельно │        │ «воды» │        │ = правда
  └────────┘         └────────┘        └────────┘        └────────┘        └────────┘
                                                          ↑ но нарратив     ↑ нарратив
                                                            «0 находок»       чинится
  находки везде = 10 (A1 B6 C1 D2), считает КОД — оптимизация LLM их НЕ меняет
```

### Паттерн 10. Дайджест данных вместо полного дампа в промпт

**Проблема.** В LLM скармливался весь снимок в КАЖДЫЙ навык → сотни тысяч входных токенов, медленно
и дорого.

**Решение.** В промпт идёт **дайджест**: точные счётчики по типам (= полный объём/scope) + маленький
сэмпл записей. LLM видит масштаб, но не каждую строку. Детекцию это не трогает (её считает код на
полных данных).

**Где в коде.** `server/runner.py` → `run_live` строит `digest` (counts + sample), лимиты в `_LIM`.

```
  ПЛОХО: полный дамп в каждый навык        ХОРОШО: дайджест
  ┌──────────────────────────┐            ┌──────────────────────────────┐
  │ [все 157 doc1c построчно] │            │ всего: 157                   │
  │ [все 61 ref1c построчно]  │  ~100k     │ по типам: {Реализация:15,    │  ~12k
  │ ... × 7 навыков           │  токенов   │   Поступление:22, СФ:14...}  │  токенов
  └──────────────────────────┘  /навык     │ сэмпл: [20 записей-примеров] │  /навык
     дорого, медленно                       └──────────────────────────────┘
                                             модель видит МАСШТАБ (полный scope),
                                             но не каждую строку. Детекцию — код.
```

**Эффект.** Входные токены ↓ в ~8 раз, качество без изменений.
**Чему учит.** *Дай модели ровно столько контекста, сколько нужно для задачи, — не больше.*

### Паттерн 11. Structured output (guided JSON) против «раздутости рассуждений»

**Проблема.** Модель пишет markdown-«воду»: преамбулы, эмодзи-заголовки, повтор задачи — тратит
токены и время на форму, а не на суть.

**Решение.** Раз у навыка чёткая задача — просим **строго JSON по схеме** (`response_format` /
guided decoding). Грамматика физически запрещает прозу вне схемы: уходит «вода», вывод парсится,
токены падают в разы.

**Где в коде.** `server/runner.py` → `_FINDINGS_SCHEMA`, `_render_findings()` (JSON → компактный
текст); передача `response_format` в вызов модели; `server/clients.py` → `chat()` принимает
`response_format`.

**Эффект.** Выходные токены ↓ в ~3 раза, время ↓ вдвое.
**Чему учит.** *Если ответ структурен — заставь модель отвечать структурой, а не текстом о структуре.*

### Паттерн 12. Параллелизм навыков + разумный потолок под ресурс

**Проблема.** Навыки в графе независимы, но выполнялись почти последовательно.

**Решение.** Навыки одной волны запускаются **параллельно** (семафор ограничивает одновременные
вызовы). Важный урок из замеров: на **общей** LLM-карте высокий параллелизм даёт троттлинг (медленнее!),
а на **выделенной** — реально ускоряет. Значение подбирается под ресурс, не «чем больше, тем лучше».

**Где в коде.** `server/runner.py` → `run_live` (топологические «волны» `_waves()`, семафор
`_LLM_CONCURRENCY`), backoff-ретрай на перегруз.

**Чему учит.** *Параллелизм упирается в узкое место (одна карта). Измеряй, а не предполагай.*

### Паттерн 13. Graceful degradation: каскад моделей + пауза ресурсов

**Проблема.** Свой LLM-инстанс может быть недоступен (пауза, обрыв). Агент не должен падать.

**Решение.** **Каскад**: сначала свой инстанс, при недоступности — внешний провайдер (дороже, но
работает). Агент опционален, ручной маршрут всегда возможен. Ресурсы (GPU) можно ставить на паузу по
расписанию для экономии — при этом система переключается на резервный канал.

**Где в коде.** `server/clients.py` → `chat()` с cascade по профилю; `ops/vast_schedule.sh` —
пауза/старт GPU-инстанса с авто-переподхватом адреса.

**Чему учит.** *Надёжность = деградация без отказа. Дешевле ≠ хрупче, если есть fallback.*

## Часть IV. Наблюдаемость и многопользовательский режим

### Паттерн 14. Observability: сквозной trace_id, метрики, «не падаем молча»

**Проблема.** Нельзя масштабировать то, что не видно; тихие сбои опаснее явных.

**Решение.** Сквозной `trace_id` (запрос → прогон → доставка), метрики (латентность, стоимость,
находки, доставки), per-skill тайминги. Нефатальные ошибки НЕ проглатываются — собираются в
`soft_errors`, логируются, видны в UI.

**Где в коде.** `server/observability.py` (trace_id, реестр метрик, структурный лог);
`server/web_api.py` → `_collect_soft_errors()`, инструментация в `execute_agent_run()`.

**Чему учит.** *Каждый шаг оставляет цифровой след. Ошибка должна быть видимой, а не молчаливой.*

### Паттерн 15. Version-aware кэш результатов (для многих пользователей)

**Проблема.** Много пользователей гоняют ТЕ ЖЕ сценарии на ТЕХ ЖЕ данных — каждый платит заново.

**Решение.** Кэш результата по ключу **agent + отпечаток версии данных + конфиг LLM**. Совпало →
мгновенный ответ без LLM (стоимость 0). Данные/агент/настройки изменились → ключ другой → пересчёт.
Никакого «слепого» TTL — инвалидация по сути.

**Где в коде.** `server/run_cache_store.py` (общий стор); `server/web_api.py` → `_run_cache_key()`,
`_data_fingerprint()` (отпечаток версии данных), проверка/запись кэша в `execute_agent_run()`.

```
  КЛЮЧ КЭША = agent_id  ::  отпечаток_версии_данных  ::  конфиг_LLM
                              (счёт + max fetched_at        (max_tokens,
                               по сущностям)                 structured, модель)

  Юзер 1 ─► [MISS] ─► полный прогон (LLM) ─► сохранить ─► результат   (~40 с)
  Юзер 2 ─► [HIT]  ─────────────────────────────────────► результат   (~0.1 с, стоимость 0)
  Юзер 3 ─► [HIT]  ─────────────────────────────────────► результат   (~0.1 с, стоимость 0)
              │
   перезалили данные / сменили агента / конфиг → ОТПЕЧАТОК ДРУГОЙ → ключ новый → [MISS] → пересчёт
   (никакого «слепого» TTL — кэш инвалидируется по сути, всегда корректен)
```

**Эффект.** Повторный прогон: секунды → ~0.1 с, стоимость → 0, результат идентичен.
**Чему учит.** *Кэшируй по СМЫСЛОВОМУ ключу (что влияет на результат), тогда кэш всегда корректен.*

### Паттерн 16. Горизонтальное масштабирование: инвалидация кэшей + leader-election

**Проблема.** На нескольких репликах сервиса: (а) in-process кэши расходятся; (б) фоновый планировщик
запускает триггеры дважды.

**Решение.** (а) **Инвалидация между репликами**: писатель шлёт сигнал (pub/sub БД) → все реплики
перечитывают кэш. (б) **Leader-election**: планировщик тикает только на реплике-лидере (распределённый
лок); лидер упал — другая перехватывает.

**Где в коде.** `server/cachebus.py` → `notify()` / `listen_loop()` (pub/sub инвалидация);
`server/triggers.py` → `_try_become_leader()` + `scheduler_loop()` (лидер по advisory-lock).

```
        Реплика A            Реплика B            Реплика C
        ┌────────┐           ┌────────┐           ┌────────┐
        │ API    │           │ API    │           │ API    │
        │ кэш ▲  │           │ кэш ▲  │           │ кэш ▲  │
        │планир.★│           │планир.·│           │планир.·│   ★ = лидер (advisory-lock)
        └───┬────┘           └───┬────┘           └───┬────┘   · = тикает вхолостую
            │  запись+NOTIFY     │ LISTEN            │ LISTEN     (нет двойного триггера)
            └────────────────────┴───────────────────┘
                          ▼  общая БД (истина)
                 ┌────────────────────────┐
                 │ Postgres: состояние +   │  (а) NOTIFY → все перечитали кэш (сходятся)
                 │ pub/sub + распред. лок  │  (б) лок → триггеры фаерит ОДИН лидер
                 └────────────────────────┘
```

**Чему учит.** *Stateless-сервис + общее состояние в БД + координация = безопасная горизонталь.*

## Сводка: чек-лист «хорошего агента» (для студентов)

1. **Истину считает код, LLM объясняет** — не доверяй факты генерации.
2. **Конверт governance** — автономия ≤ потолок, внешние действия под HITL.
3. **Данные через контракт** (Data Plane, ключ `entity`), не из сырых систем.
4. **Версионная свежесть**, а не наивный TTL.
5. **Least-privilege/ABAC** на шлюзе — агент видит только своё.
6. **Явные старт (trigger) и выход (out)** с dry_run/HITL по умолчанию.
7. **Знание из RAG с провенансом**, не из памяти модели.
8. **Дай контекст-дайджест**, а не всё подряд.
9. **Structured output** там, где ответ структурен.
10. **Параллель под ресурс** + fallback-каскад (деградация без отказа).
11. **Сквозная наблюдаемость**, ошибки не молчат.
12. **Кэш по смысловому ключу** + координация реплик для мультиюзера.

> Все паттерны реализованы в ABOP; имена функций/файлов выше — точки входа для разбора кода на
> семинаре. Эндпоинты и секреты намеренно опущены — важна суть архитектуры.
