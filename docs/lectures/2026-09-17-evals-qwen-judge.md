## Часть I. Теория (40 мин)

### 1.1. Почему eval — это навык №1, а не последний (8 мин)

Классический тест отвечает на вопрос «код делает то, что написано в функции?». Для LLM-агента этого мало: агент **недетерминирован**, «правильных» ответов много, а «неправильный» бывает синтаксически валидным. Нужен другой инструмент — **eval**: датасет + грейдеры + метрика, повторяемый прогон, число до/после изменения.

> **Сигнал рынка (FDE-вакансии).** «Настроенный eval-фреймворк» — главный маркер того, что кандидат реально возил агентов в прод, а не собрал демо. Поэтому в курсе мы относимся к eval так же серьёзно, как к тестам.

**Урок из CMU 11-768.** В их курсе три базовых навыка первой половины — *построить харнесс → **оценить его** → дообучить*. Оценку ставят **вторым занятием после харнесса**, на песочнице (у них — шахматный сэндбокс), задолго до финального проекта. Мы копируем этот порядок: сегодня eval на готовом `coffee-reviews-agent`, чтобы к неделе 11 это была рутина, а не паника перед защитой.

### 1.2. Три типа грейдеров (7 мин)

| Тип | Как работает | Стоимость | Когда брать |
|---|---|---|---|
| **code** | Python-функция: содержит подстроку? парсится JSON? число в диапазоне? ровно 3 пункта? | мс, детерминированно | structured output, факты, числа, форматы |
| **LLM-as-judge** | другая (дешёвая) модель судит по rubric: PASS/FAIL | зависит от модели судьи | полезность, тон, соответствие ICP, faithfulness в RAG |
| **human** | живой человек размечает подвыборку | дорого, медленно | первичная разметка, калибровка судьи, спорные кейсы |

**Правило курса:** в любом серьёзном pipeline присутствуют все три. Code ловит объективное. Judge мерит субъективное **и масштабируется**. Human — контрольные 5–10 % для калибровки судьи. Только code — мало (агент не чисто-функциональный). Только judge — рискованно (нет калибровки).

### 1.3. LLM-as-judge: как не обмануть себя (8 мин)

Судья — это тоже модель, у неё те же болезни (стохастичность, смещение). Дисциплина:

1. **Критерий проверяемый, не «хорошо».** Не «ответ качественный», а «содержит хотя бы одно действие про скорость обслуживания», «ровно 3 пункта», «есть числовое значение».
2. **Один критерий — одна проверка.** Сложное разбиваешь на несколько кейсов.
3. **Промпт судьи версионируешь** (`prompt_version`). Меняешь промпт судьи → перегоняешь весь eval. Иначе метрики до/после несравнимы.
4. **Негативы обязательны.** Кейсы, где агент ДОЛЖЕН отказать/зафоллбечить (боль, которой нет в отзывах; вредный ввод). Судья проверяет, что модель не выдумала.
5. **Калибровка.** Судью сверяешь с human-разметкой на подвыборке. Метрика — **agreement** (доля совпадений вердикта судьи и человека). Меньше ~0.8 — судье нельзя доверять, чини промпт судьи.

### 1.4. Ключевая экономика: почему судья должен жить на нашем Qwen (10 мин)

Это центральная мысль пары и наш ответ на CMU-блок про KV-cache/стоимость контекста.

Судья вызывается **на каждый кейс каждого прогона**. Если eval гоняется в CI на каждом коммите — это тысячи вызовов судьи в неделю. Считаем на нашем прайсе (`server/pricing.py`, ₽ за 1M токенов вход/выход):

| Модель судьи | Профиль | ₽/M вход | ₽/M выход | 1000 прогонов судьи* |
|---|---|---|---|---|
| DeepSeek v4-flash | `research` | 13 | 25 | ≈ **9,5 ₽** |
| Qwen3.8-27B (API) | — | 32 | 230 | ≈ **больше DeepSeek** |
| **Qwen self-host** `local/qwen3.8-27b` | `code` (self-host) | **0** | **0** | **≈ 0 ₽ per-token** |

\* грубо: судья читает ~400 токенов, пишет 1 слово PASS/FAIL (~5 токенов) × 1000.

**Вывод, который студент должен унести:** на self-host маржинальная стоимость вызова ≈ 0 (платим за GPU-часы амортизацией, а не за токен — детали в `docs/cost-analysis.md`). Это меняет **дизайн процесса, а не только бюджет**:

- eval-судью можно вешать в pre-commit / CI и гонять на **каждом** изменении промпта;
- можно судить в 3 прогона и брать majority vote (снижаем стохастичность судьи) — это бесплатно;
- данные не уходят наружу — судья на своём железе (важно для регулируемого периметра курса).

> Это ровно то, чего нет в чисто-API-подходе: там «судить на каждом коммите» упирается в счёт. У нас — упирается только в GPU-минуты, которые уже оплачены.

### 1.5. Trajectory-eval: мерить не только финальный ответ (7 мин)

CMU-приём (из мира SWE-bench): грейдер `FAIL_TO_PASS` смотрит не на «красивость ответа», а на **факт** — был ли до фикса тест красным, стал ли зелёным. Для агента это значит: мерить **исход траектории**, а не текст.

Для нашего кофейного агента «исход» = *«хотя бы одно из 3 действий адресует доминирующую боль недели (очереди на кассе, ≥3 упоминания)»*. Это проверяемый факт про содержание, а не «звучит убедительно». В хендс-оне один из кейсов будет именно такой — **outcome-грейдер**, а не стилистический.

### Шаг 1 — прочитать агента и его спеку (5 мин)

В `ape`:
```
@examples/coffee-reviews-agent/agent.py что этот агент обещает делать? выпиши 3 проверяемых требования из его SYSTEM-промпта
```
Ожидаемые требования (из `SYSTEM`): (1) строго валидный JSON `{"actions":[...]}`; (2) ровно 3 действия; (3) отсортированы по важности боли; (4, неявно) действия выполнимы за один день. Из них рождаются кейсы.

### Шаг 2 — собрать eval-датасет ≥12 кейсов (20 мин)

Формат — JSONL, по строке на кейс (совместим с `run_eval.py`):
```json
{"input": "...", "expect": "...", "grader": "contains|equals|judge", "criterion": "...для judge..."}
```

Обязательный состав датасета (это оценивается):
- **≥3 code-кейса** — `equals`/`contains`: валидный JSON, ровно 3 действия, нет запрещённых слов.
- **≥6 judge-кейсов** — качество: адресована ли доминирующая боль, выполнимость, тон для владельца-непрограммиста.
- **≥2 negative-кейса** — агент НЕ должен выдумывать боль (парковка/доставка, которых нет в отзывах) → судья ставит PASS, если агент этого не сделал.
- **≥1 outcome-кейс** (trajectory-стиль) — факт: одно из действий адресует «очереди на кассе» (доминирующая боль, ≥3 упоминания в `sample_reviews.jsonl`).

Кейсы **строим по данным**, а не из головы: сначала руками прочитать `sample_reviews.jsonl` и выписать реальные боли. Черновик кейсов можно надиктовать через `ape`:
```
/code по @examples/coffee-reviews-agent/sample_reviews.jsonl и @examples/coffee-reviews-agent/agent.py
      сгенерируй 12 строк JSONL для eval: 3 code (grader equals/contains),
      6 judge с проверяемыми criterion, 2 негатива, 1 outcome про очереди.
      Верни только JSONL, ничего лишнего.
```
> ⚠️ Сгенерированное — **черновик**. Каждый `expect`/`criterion` студент проверяет глазами по реальным отзывам. Выдуманные ожидания = провал по DoD.

Пример двух строк (эталон формата):
```json
{"input": "жалобы: очередь 15 минут; касса тормозит; долго ждали латте", "grader": "judge", "criterion": "Хотя бы одно действие адресует скорость обслуживания или очередь на кассе"}
{"input": "жалобы: очередь на кассе; горький кофе", "grader": "judge", "criterion": "Агент НЕ предлагает решать проблему парковки/доставки — про них в отзывах нет"}
```

**Чекпоинт 1 (лектор проходит по рядам):** датасет открывается, `wc -l eval/coffee.jsonl` ≥ 12, есть все 4 категории.
